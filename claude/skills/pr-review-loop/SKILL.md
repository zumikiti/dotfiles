# PRレビュー・修正ループ

指定された PR を、サブエージェントによる並列レビューと修正・コミットを交互に繰り返して仕上げる。
評価項目・緊急度基準・指摘の返し方は `pr-review` スキルのものを使う（重複定義しない）。出力形式はラウンドをまたぐため本スキルで定義する。

## 使用方法

```
/pr-review-loop <PR番号> [--max-rounds N]   # 既定 3 ラウンド
```

- `$ARGUMENTS` の最初の数値を PR 番号、`--max-rounds N` があれば N をラウンド上限とする。引数が無ければ PR 番号を尋ねる
- 1 ラウンド = レビュー + 修正。上限ラウンドではレビューのみ行い、修正せず残指摘を最終レポートに出す（レビューされていない修正を push しないため）。CI 失敗の修正はラウンドに数えず、別枠で最大 2 回

## 前提

- カレントの worktree が対象 PR のブランチであること（`gh pr view <N> --json headRefName` と `git branch --show-current` を照合する。違えば作業を止めてユーザーに知らせる）
- サブエージェントの `model` は `subagent-model-policy` スキルに従って必ず明示する
- コミットは `commit` スキルに従う
- push・PR 本文の書き換えは**ループが収束してから**行う。収束後の push と `gh pr edit` は**ユーザーに確認せず実行してよい**（このスキルの起動がその許可。ただし実行環境の権限設定が優先する）

## 手順

### 0. 準備

1. `gh pr view <N> --json title,body,files,commits,headRefName,baseRefName,additions,deletions` と `gh pr diff <N>` を取得
2. PR 本文の「やった事 / やらない事 / スコープ外」を読み、**この PR で直してよい範囲**を把握する。スコープ外の指摘はコード修正せず、PR 本文への追記候補として別に積む
3. 差分の性質からレビュー観点を決める。`pr-review` の6項目を機械的に全部立てるのではなく、差分に効く観点を 2〜4 本に束ねる（インフラ差分のみ、6項目に無い「運用の整合性」を足す）
   - アプリコード中心: コード品質+過剰設計 / セキュリティ / メンテナンス性+型安全性
   - インフラ・CI 中心（workflow, task definition, Dockerfile 等）: **デプロイ運用の整合性・障害リスク** / セキュリティ / コード品質+重複
   - 両方にまたがる差分: インフラ・CI 中心の3本を使い、コード品質+重複の担当にアプリ側の型安全性・メンテナンス性も持たせる（観点は最大4本まで）
   - 「運用の整合性」観点は、共有リソースの奪い合い・適用順序の依存・「緑なのに壊れる」経路を具体的に洗わせる。この観点は判断を伴うので opus に倒す

### 1. ラウンド 1: レビュー

観点ごとにサブエージェントを **1メッセージで並列起動**する（差分が小さくても委譲する。再レビューを修正者から独立させるため）。プロンプトに必ず含めること:

- worktree の絶対パスと「ここから出ない」「読み取り専用・変更/コミット/push 禁止」
- PR 番号、差分の取得コマンド、比較対象となる既存ファイル（コピー元など）
- 担当観点と、具体的に洗う項目の列挙
- 出力形式: 「ファイル:行番号 + 問題（何がどう壊れるか） + 改善案 + 緊急度（`pr-review` の 🔴/🟡/🟢 基準）」
- **推測と確認済み事実を区別し、断定できないものは「未確認」と明記**させる
- 良い点も 1〜2 点挙げさせる（指摘の返し方は `pr-review` の「指摘の返し方」に従う）

サブエージェントが走っている間、自分で同じファイルを読み直して重複調査しない。待つ。

### 2. 集約と仕分け

報告が揃ったら、指摘を次の3つに仕分ける:

| 区分 | 扱い |
|---|---|
| **本 PR で直す** | スコープ内で、コード/設定/コメントの変更で解消できるもの |
| **PR 本文に書く** | 適用順序・運用注意・未確認事項など、コードでは解消できないが読み手が知るべきもの |
| **本 PR 外** | 別リポジトリ・別 PR・既存踏襲でスコープ外のもの。最終レポートに「本 PR 外」として残す |

仕分けの判断基準:
- 共通化・抽象化の提案は、片方が廃止予定なら **一時的重複として許容**し、`deliberate:` コメントで昇格条件を残す方に倒す
- 環境変数化・設定化の提案は、値が環境間で変わらないなら **しない**（変わらぬ値に config を作らない）
- 「未確認」のまま残った指摘は、実挙動を確認できるまで**コードを触らず**、PR 本文に「未確認・初回デプロイ後に確認」と書く
- 外部から拾ってきた仕様（アクションの input 名や既定値など）は、修正に使う前に `gh api` 等でピン留め SHA 時点の実体を確認する

ラウンドのレポートを `pr-review` の出力形式で表示する（ユーザーは途中経過を見たい）。総合評価（X/10）はこの集約時に `pr-review` の緊急性レベル基準で自分が付け、最終レポートで初回と最終を並べる。

### 3. 修正とコミット

1. 「本 PR で直す」を適用する。構文確認は YAML が `python3 -c "import yaml,sys; [yaml.safe_load(open(f)) for f in sys.argv[1:]]" <files>`、JSON が `jq empty <file>`
2. `commit` スキルに従い、論理単位でコミットする（衝突対策 / 完了判定 / ドキュメント、のように分ける）
3. pre-commit hook（lefthook 等）が PATH に無くて走らなかった場合、node_modules が無くて lint/typecheck が回せない場合は、**その事実を記録して最終レポートに書く**（CI に委ねる旨）
4. 「PR 本文に書く」は、元本文を scratchpad の `pr-body-orig.md` に退避し、**そのコピー** `pr-body-new.md` に追記していく（追記分だけのファイルで `gh pr edit` すると元本文が消える）

### 4. ラウンド N+1: 再レビュー

サブエージェントを再起動する。ラウンド 1 との違い:

- プロンプトに**「前ラウンドで指摘され、修正したと主張している内容」を列挙**し、それぞれ「解消済み / 部分解消 / 未解消」で判定させる
- 加えて「修正が新たな問題を持ち込んでいないか」「残っている高・中緊急度はあるか」を問う
- **残っていなければ「本 PR 内で対処すべき指摘なし」と明言させる**（収束判定に使う）
- 差分が縮むにつれエージェント数を段階的に減らし、最終確認は1 エージェントでよい

再レビューの指摘を再び 2. で仕分けし、3. で直す。

### 5. 収束と終了

次のいずれかで止める:

- サブエージェントが「本 PR 内で対処すべき指摘なし」と明言した
- 残った指摘が低緊急度のみで、直すより記録の方が価値が高い
- `--max-rounds` に達した（達した場合は残指摘を最終レポートに明示する）

最終レポートを出す:

```
📊 最終レビューレポート
PR番号 / 評価日時 / ラウンド数

### 解消済み（各ラウンドの指摘）
| 指摘 | 対処 |

### 本 PR 外・未確認として残すもの
- 🔴/🟡/🟢 + 内容 + どこで/いつ確認するか

📈 総合評価: 初回 X/10 → 最終 Y/10

### 手元の状態
- 未 push コミット N 件（一覧）
- hook / lint / typecheck の実施状況
- PR 本文の更新案の有無
```

その後、**確認せずに** `git push`（上流未設定なら `git push -u origin HEAD`）を実行し、`pr-body-new.md` が `pr-body-orig.md` と異なるときだけ `gh pr edit <N> --body-file <pr-body-new.md>` を実行して、PR URL とコミット数を報告する。
PR 本文の差分（何を足し、何を変えたか）は報告に添え、全文は求められたときだけ出す。

### 6. CI の見届け

push 後に CI があれば、正常完了まで見届ける。

- `gh pr checks <N> --json name,bucket,link` を Monitor（30 秒間隔・`pending` が無くなったら終了）で監視する。pending 中は終了コード 8 を返すが異常ではない。待っている間に同じ調査を重ねない
- 全部 `pass` / `skipping` なら、その旨を報告して終了
- `fail` / `cancel` があれば、`link`（`.../actions/runs/<run-id>/job/...`）から run-id を取り、ログ（`gh run view <run-id> --log-failed`）を読んで**本 PR の変更が原因か**を切り分ける
  - 本 PR 起因: 修正 → コミット → push（確認不要）→ 再度 CI を見届ける（「使用方法」の CI 修正枠）
  - 既知のフレーキー・無関係な失敗: `gh run rerun <run-id> --failed` で再実行し、再度見届ける。それでも落ちるなら原因と共に報告する
- 「hook / lint / typecheck は CI 委ね」と書いた項目は、ここで CI の結果に置き換えて報告する

## やってはいけないこと

- 指摘を「方針に合わない」だけで却下する。却下するなら根拠を書く
- push だけして CI を見届けずに終える
- スコープ外（PR 本文の「やらない事」）に踏み込む修正。ただし共有リソース衝突の回避のように**既存側に最小の変更が必要な場合**は、変更内容を PR 本文に明記した上で行ってよい
