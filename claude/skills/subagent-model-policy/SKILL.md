# サブエージェントのモデル使い分け方針

サブエージェントを起動するときは、`model` パラメータを省略せず必ず明示する。
`model` は、呼び出し時の指定 → エージェント定義の frontmatter → 環境変数 `CLAUDE_CODE_SUBAGENT_MODEL` → 親セッションのモデル の順で決まる。省略すると、親が Fable 5.1 のセッションでは Sonnet の 5 倍の単価で動いてしまう。
組み込みの Explore / Plan エージェントも同じ（省略すると親を継承する）。

## 前提（2026-10-07 時点の較正値）

別名（`sonnet` / `opus` / `haiku` / `fable`）は各ティアの推奨版へ自動で追従する。この方針が前提にしている解決先と単価は次のとおり。

| 別名 | 現在の解決先 | 入力 / 出力（$/MTok） | Sonnet 比 |
|---|---|---|---|
| `fable` | Claude Fable 5.1 | 10 / 50 | 5 倍 |
| `opus` | Claude Opus 5.5（2026-09-22） | 4 / 20 | 2 倍 |
| `sonnet` | Claude Sonnet 5.5（2026-09-28） | 2 / 10 | 1 倍 |
| `haiku` | Claude Haiku 4.5（Haiku 5.5 は予告済み・未リリース） | 1 / 5 | 0.5 倍 |

別名の解決先が変わったとき（特に Haiku 5.5 リリース時）は、この表と下の配分を見直す。

## 使い分け

| タスクの種類 | モデル指定 |
|---|---|
| 機械的な大量作業で、出力を機械的に検証できるもの（複数ファイルの定型フォーマット整形、テンプレートからの定型文量産、固定ルールでの分類・抽出）。コードを読んで判断する工程を含まないこと | `model: "haiku"` |
| 調査（grep・git履歴・ファイル横断の事実確認、仕様が明確な範囲でのコードベース内の原因調査、既存の MCP / API からのデータ収集） | `model: "sonnet"` |
| コーディング・実装（範囲が明確な機能追加・バグ修正・テスト追加・定型的なリファクタ） | `model: "sonnet"` |
| 設計判断・仕様解釈を含む調査、複数ソースを横断して「何が問題か」自体を見極める調査、原因の見当がつかないデバッグ、Web 検索を主とするリサーチ | `model: "opus"` |
| 広範囲に影響するリファクタや設計判断を伴う実装 | `model: "opus"`（まずユーザーに確認する） |

## 判断に迷うとき

- 「何を探すか／何を作るか」が明確なら Sonnet、「探しながら・作りながら判断する」なら Opus
- Haiku は「手順どおりにやれば終わる」かつ「結果を機械的に検証できる」場合に限る。コードを読んで判断させるなら Sonnet に上げる。Haiku で失敗して Sonnet でやり直すと、節約分（Sonnet の半額）は消える
- 調査寄りの中間タスク（設計判断を含む調査など）→ Opus に倒す。Opus は Sonnet の 2 倍で済み、やり直しより安い
- `fable` をサブエージェントに指定するのは、親と同等の判断力が本当に必要な場合に限る（原則不要）
- Workflow スクリプト内の `agent()` 呼び出しにも同じ方針を適用する（`opts.model`）。Workflow では `opts.effort` も使えるので、機械的な段階は `effort: "low"`、検証・判定の段階だけ高くする

## サブエージェントへの指示で補うこと（Sonnet 5.5 の既知の癖）

- Web 検索や MCP ツールで確認させる調査では「自分の知識で答えず、必ずツールで確認すること」とプロンプトに明記する（接続ツールがあっても手持ちの知識で答える傾向が公式に報告されている）
- コーディングを任せるときは「変更後にテスト／型チェック／ビルドを実際に走らせてから完了報告すること。構文チェックだけでは不可」と明記する
